Subject: mm/hugetlb: fix validation of unsupported HugeTLB orders
Date: Wed,  4 Nov 2026 15:18:57 +0800

Commit 7ce6048d3a7d ("loongarch: drop ranges for definition of
ARCH_FORCE_MAX_ORDER") removed the ARCH_FORCE_MAX_ORDER ranges for
LoongArch.  Besides dropping unreasonable upper limits, this allowed
values below the architecture defaults.

With 16KB pages, LoongArch defaults ARCH_FORCE_MAX_ORDER to 11, matching
HUGETLB_PAGE_ORDER.  Forcing it to 10 while enabling HugeTLB permits
order-11 HugeTLB folios even though MAX_FOLIO_ORDER is 10.  LoongArch does
not select ARCH_HAS_GIGANTIC_PAGE, so this violates the generic MM
assumption that folios cannot exceed MAX_PAGE_ORDER.

This invalid configuration is accepted by Kconfig.  BUILD_BUG_ON_INVALID()
does not reject it either because it only checks whether the expression is
valid and never evaluates the comparison.  Detection is left to the
runtime warning in hugetlb_add_hstate(), after earlier boot paths may
already have used the invalid configuration.

When an invalid HugeTLB order can be identified at build time, reject it
there.  Otherwise, reject it at runtime before the mismatch propagates
further.  Use MAYBE_BUILD_BUG_ON() so constant violations fail the build
while dynamically determined orders are checked at runtime.
