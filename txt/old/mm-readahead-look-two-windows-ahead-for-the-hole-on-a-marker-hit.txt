Subject: mm/readahead: look two windows ahead for the hole on a marker hit
Date: Thu, 22 Oct 2026 23:24:33 +0800

When a reader hits a folio marked for readahead that the readahead state
does not expect, page_cache_async_ra() starts the next readahead at the
first hole within one window after the folio.  If that window is fully
cached, it reads nothing.

memcpy() in glibc loads the end of a large source before copying it
forward, so a loader that copies a file mapping out in pieces of a few
megabytes faults at the end of each piece first.  mmap read-around then
reads a window centered on that fault, which reaches more than one window
past the readahead marker the copy has yet to hit.  When the copy reaches
the marker, there is no hole within a window, no readahead is issued, and
the next piece faults on its end again.  Every piece then gets a
synchronous read-around of order-0 folios, and threads copying parts of
one file also contend on the i_pages lock to insert them.  A copy from
offset 0 avoids this as its first read-around is clamped to the start of
the file.

Look up to two windows ahead for the hole, which reaches past such a
read-around, so the reader keeps an asynchronous window and its folio
order keeps ramping up.

Copying a 16 GiB file out of a private mapping with memcpy() in 8 MiB
pieces, read_ahead_kb 8192, cold page cache, 32 vCPU VM, mean of two
runs:

                                  before    after
  1 thread from offset 2 GiB     7.62 s    2.00 s
  8 threads, one range each      3.26 s    1.08 s
  32 threads, one range each     4.05 s    1.34 s

Random touches read the same amount, and pread() copies and copies that
interleave 7 MiB chunks across threads take the same time within
run-to-run noise.
