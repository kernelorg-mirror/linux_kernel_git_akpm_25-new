From: Andrew Morton <akpm@linux-foundation.org>
Subject: mm: notify pre-content listeners on mremap and remap_file_pages
Date: Sat, 21 Nov 2026 17:02:34 -0800

The pre-content mmap hook covers a file range before it becomes accessible.
Growing a file-backed VMA with mremap() and changing its file offsets with
remap_file_pages() can expose a range without calling that hook. A local
user with ordinary file access can therefore read data before a pre-content
handler has filled it, or without giving that handler a chance to deny the
new range.

Notify the handler for the newly exposed tail on mremap() expansion and
for the target file range in remap_file_pages(). The latter already drops
mmap_lock before calling security_mmap_file(). For mremap(), drop the write
lock before calling the potentially blocking handler, then verify the file
and offset under the reacquired lock. Recheck the VMA and map count before
changing anything. If another thread has replaced the mapping, fail with
-EAGAIN instead of using a permission decision for the wrong file range.
Moves and shrinking do not expose new file offsets.

This is reachable by an unprivileged caller with read access to a marked
file; remap_file_pages() also requires a writable shared mapping. It does
not grant access to files that ordinary permissions prevent the caller
from opening. The failure matters when a pre-content handler uses the
notification to fill file data or to enforce a range-specific denial.
