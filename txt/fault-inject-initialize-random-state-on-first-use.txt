Subject: fault-inject: initialize random state on first use
Date: Thu, 5 Nov 2026 10:01:33 -0800

setup_fault_attr() is called by fault-injection boot parameter handlers
before slab and workqueues are initialized.  Its prandom_init_once() call
expands to DO_ONCE(), whose static-key disabling path allocates memory and
schedules work.  A valid fault-injection boot parameter can therefore
crash the kernel before boot completes.

There are also separate prandom_init_once() calls in the debugfs and
configfs setup paths.  Each expansion has its own guard, so configuring
another interface can reseed the shared random state while injection is
already active.

Initialize each CPU's random state on its first draw instead, and remove
the three configuration-time initialization calls.  Seed it using
random_get_entropy() and the CPU number, retaining the warmup used by
prandom_seed_full_state().  This avoids allocation, workqueues and the
cryptographic RNG's potentially sleeping locks on PREEMPT_RT.

The seed is not cryptographically strong, and may be deterministic early
in boot when no entropy source is available.  Fault injection does not
require cryptographic unpredictability.

Disable local interrupts around initialization and generation.  Fault
injection can run from interrupt handlers, including NVMe completion, so
an interrupt must not observe partially initialized state or overwrite an
interrupted generator update.
