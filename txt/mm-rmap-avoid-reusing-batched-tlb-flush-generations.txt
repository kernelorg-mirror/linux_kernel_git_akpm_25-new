From: Andrew Morton <akpm@linux-foundation.org>
Subject: mm/rmap: avoid reusing batched TLB flush generations
Date: Tue, 17 Nov 2026 17:49:27 -0800

mm->tlb_flush_batched resets to 1 when its 15-bit pending count grows
large.  A concurrent flush can read 1, flush, then see 1 again after the
reset and mark newer unmaps as flushed.  A subsequent caller can skip a
needed TLB flush and leave a stale writable translation.

Use the existing atomic_t as two bits instead of counting generations. 
PENDING records a deferred unmap.  A caller atomically changes PENDING to
FLUSHING before flushing.  Any other caller seeing FLUSHING flushes for
itself rather than treating the first flush as complete.  An unmap that
arrives during the flush sets PENDING again.  The first caller clears only
FLUSHING after its flush, preserving that new work.  There are no
generation values to wrap or for a delayed flusher to write back, and
mm_struct does not grow.

The unmapper holds the PTE lock through the clear and PENDING update. 
smp_mb__before_atomic() orders the clear before atomic_or(), which has no
memory ordering of its own.  A successful cmpxchg takes ownership before
flush_tlb_mm().  The flush completes before atomic_andnot() clears
FLUSHING.  flush_tlb_mm() provides the required ordering of TLB
invalidation completion; the final atomic operation only needs to preserve
PENDING if an unmap races with that clear.

All callers that check the state hold the relevant PTE lock.  Once a
checker acquires that lock, its zero-state read cannot miss an unmap which
published PENDING before releasing it.  A zero read, including a failed
cmpxchg returning zero, can also follow a completed flush by another
owner.  An unmap under another PTE lock cannot clear the entry this
checker is about to change.

Initialize the state for a new mm: dup_mm() copies the parent's mm_struct
before mm_init(), so the child must not inherit an in-progress flush with
no owner.

The owner executes a cmpxchg before flush_tlb_mm() and an atomic_andnot()
afterward, rather than one post-flush cmpxchg in the counter code.  This
adds an atomic read-modify-write operation to an uncontended pending-flush
call.  The unmap path also replaces a compiler barrier with
smp_mb__before_atomic(), which can cost more on weakly ordered CPUs.

Concurrent flushes can cause additional full-mm flushes.  If an unmap sets
PENDING while the owner flushes, a second checker can flush and cover that
unmap, but cannot mark it complete.  The owner clears only FLUSHING,
leaving PENDING for a third checker to flush again.  With counters, the
second checker could record the newer generation as flushed.  These costs
have not been measured.
