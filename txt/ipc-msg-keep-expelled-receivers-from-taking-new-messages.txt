Subject: ipc/msg: keep expelled receivers from taking new messages
Date: Wed, 18 Nov 2026 12:28:21 +0900

Patch series "ipc/msg: prevent reads after queue permission revocation".

A process whose read access to a SysV message queue was revoked by IPC_SET
can receive a message sent afterward.  A blocked receiver needs no
capability and can have a different UID from the queue owner.  Patch 1
prevents delivery to a receiver awakened by IPC_SET.  Patch 2 closes the
window between the read permission check and waiter insertion.

IPC_SET wakes all blocked receivers, including those whose read access is
unchanged.  Each leaves q_receivers when it runs; a receiver that must
wait again rejoins at the tail, so IPC_SET can change their FIFO order. 
Until they run, a sender queues a message instead of handing it to one of
them.  An authorized receiver may then take it from the queue.

Waking only receivers whose access was revoked is not a small change. 
IPC_SET runs in the setter's context, but ipcperms() checks current's
credentials and invokes the security hook.  Deciding which waiters lost
access would need a way to check each receiver's credentials and security
policy, with appropriate audit behavior.  Leave that separate from this
fix; IPC_SET is infrequent, and the existing wake-all behavior remains.

This patch (of 2):

IPC_SET sets a blocked receiver's result to -EAGAIN so it retries its read
permission check.  expunge_all() leaves the receiver on q_receivers; a
sender can hand it a new message before it wakes.  If IPC_SET revoked its
read access, it receives data that was sent after the revocation.

Mark every receiver that expunge_all() touched and skip it in
pipelined_send().  Keep it linked until it wakes so IPC_RMID can still
find it and change its result to -EIDRM.  The sender queues the message
instead.  On retry, a receiver with read access can take it from the
queue; a receiver whose read access was revoked gets -EACCES.
