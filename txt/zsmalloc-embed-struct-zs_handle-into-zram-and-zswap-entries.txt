Subject: zsmalloc: embed struct zs_handle into zram and zswap entries
Date: Wed, 11 Nov 2026 15:46:32 +0900

zsmalloc allocates an object from handle_cachep for every stored object,
just to have a stable address which compaction and page migration can
update when the object moves.  Both zram and zswap already have per-entry
structures that hold the handle, so we basically keep a pointer to a
pointer, which costs 8 bytes per stored object, slab alloc/free on every
store and free, and one more memory load on every access.

Make struct zs_handle public and embed it into zram_table_entry and
zswap_entry (their sizes don't change), so that zsmalloc writes object
location directly there, and remove handle_cachep.  zs_malloc() now takes
a handle pointer and returns an error code, zs_free() resets the handle.

Since compaction and migration update the handle in place, it must be
naturally aligned, must not be on the stack (zs_malloc() warns about
both), must not be copied, and must stay allocated until zs_free() or
zs_rebind_handle().  zram recompression allocates a new object before it
frees the old one, so it uses zram->recomp_handle, protected by
->dev_lock, and zs_rebind_handle() moves the new object to the slot
handle.  zram recompression is the only user of zs_rebind_handle().

This saves 8 bytes per stored page, e.g.  2MB per 1GB of swapped out 4K
pages.  Since handle is per-entry the memory savings scale.
