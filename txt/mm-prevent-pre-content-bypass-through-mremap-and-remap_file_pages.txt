From: Andrew Morton <akpm@linux-foundation.org>
Subject: mm: prevent pre-content bypass through mremap and remap_file_pages
Date: Sat, 21 Nov 2026 20:26:34 -0800

An fsnotify pre-content handler sees the range passed to mmap(), but
mremap() can extend a file mapping beyond that range without notifying it.
A process with ordinary read access can map a populated page, grow the
mapping, and fault on the newly exposed page.  It can then read zeroes
from an unfilled hole instead of the contents the handler would have
supplied, or read bytes that a range-specific handler would have denied. 
This does not bypass file-opening permissions.  remap_file_pages() can
likewise replace a file range without notifying the handler.

A previous fix rejected every file-backed mremap() growth for which
FMODE_FSNOTIFY_HSM was set. That breaks growth even when the handler
would allow it. The mode bit is also set for an ordinary FAN_ACCESS_PERM
watch, so the rejection affects files without any pre-content watch.

For growth beyond the existing VMA end, hold a reference to the file and
ask the pre-content handler about only the newly exposed file range.
Drop mmap_write_lock before calling the handler, which can block while
it fills the range. After reacquiring the lock, repeat the VMA checks:
if the file or newly exposed range changed meanwhile, request permission
for the current range instead. A denial leaves the mapping unchanged.
Growth within the already mapped file range needs no new notification.
A legacy FAN_ACCESS_PERM watch without a pre-content mark receives no
FAN_PRE_ACCESS event and does not cause mremap() to fail.

Call the same pre-content hook in remap_file_pages() before it acquires
mmap_write_lock, using the replacement file range.

An active pre-content handler can now delay or deny growth. It may also
receive a permission event for a remap that subsequently fails for an
unrelated reason, or another event if the mapping changes while it is
responding. No blanket EOPNOTSUPP restriction remains.
