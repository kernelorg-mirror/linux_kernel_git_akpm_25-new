Subject: selinux: recheck backing-file permissions on remap_file_pages()
Date: Sat, 21 Nov 2026 17:58:52 -0800

remap_file_pages() rechecks mmap permission on vma->vm_file before
replacing a shared file mapping.  On a stacked filesystem that pointer can
refer to a backing file opened with the mounter's credentials.  SELinux
then checks the caller against the backing file's opener SID and inode,
rather than the saved user file, and can reject a permitted remap with
EACCES.  A confined process can reach this using its own writable shared
overlayfs mapping; it does not need mount privileges.

Use the user path and saved opener SID for the caller check.  Recheck
intermediate mounters and the backing file as mprotect() does, while
retaining the existing FILE__MAP check for the remap.  Ordinary files keep
their existing checks.  This repairs the demonstrated denial and avoids
omitting backing-layer checks; an access-control bypass was not
demonstrated by the report.  The separate missing fsnotify pre-content
notification is not addressed here.

Testing: On A, without this patch, uid 65534 in
user_u:user_r:user_t:s0, with SELinux enforcing, opened and mapped a
writable shared overlayfs file. mmap() and mprotect() returned 0, but
remap_file_pages() returned EACCES and left page A (byte 65) mapped.
The AVC denied { use } on an fd from user_t to its kernel_t opener;
the recorded backing inode matched the overlay upper file. An ordinary
ext4 file remapped successfully in the same context.

On B, with this patch alone, the overlay remap returned 0 and read the
selected page B (byte 66). After the initial mapping, denying write on
the user-visible file returned EACCES with a file { write } AVC.
Independently denying map permission on the upper file to the saved
mounter SID returned EACCES with a backing-file { map } AVC. The ordinary
ext4 control still succeeded. No kernel warning or oops was observed.
