From: Andrew Morton <akpm@linux-foundation.org>
Subject: iommufd: enforce memfd write seals for file mappings
Date: Tue, 3 Nov 2026 19:20:00 +0000

IOMMU_IOAS_MAP_FILE pins memfd folios directly, without checking file
access permissions or write seals. A writable IOAS mapping can therefore
modify a file supplied through a read-only descriptor, or modify memfd
contents after F_SEAL_WRITE has been installed.

Yiming Qian and Keenan Dong reported this in "iommu/iommufd: Require
write access for writable MAP_FILE mappings". Their proposal checked
FMODE_WRITE and held writable-mapping accounting for the lifetime of the
iopt_pages object. In that discussion, Jason Gunthorpe requested a
companion MM API to manage this instead of open-coding it in IOMMUFD.

Implement that approach with memfd_pin_folios_begin() and
memfd_pin_folios_end(). Retain the proposal's lifetime accounting,
including intervals without pinned pages: an IOAS without a domain can
defer pinning until a later attachment, and copied mappings can keep the
pin source alive after the original mapping is removed.

Also require FMODE_READ and explicitly check F_SEAL_WRITE and
F_SEAL_FUTURE_WRITE. The earlier proposal's mapping_map_writable() check
alone does not reject F_SEAL_FUTURE_WRITE, which does not make the
writable-mapping counter negative. Serialize the seal check and writable
claim with seal installation using the inode lock.

Keep the claim with the shared iopt_pages object and release it after its
last user has dropped all pins. F_SEAL_WRITE then cannot succeed while
future writable pins remain possible. F_SEAL_FUTURE_WRITE prevents new
writable authorizations without revoking existing ones. Read-only
mappings remain permitted on write-sealed files.

Add selftests for both write seals, descriptor permissions, deferred
pinning, copied-mapping lifetime and failed-map cleanup.
