Subject: fs/proc/task_mmu: fix lost maps entries above 2^63
Date: Tue, 13 Oct 2026 17:21:06 +0200

When a read of /proc/pid/{maps,smaps,numa_maps} resumes, m_start() rewinds
*ppos to priv->last_pos so that the vma which did not fit into the
previous buffer is shown again.

The last_addr > 0 test is intended to exclude the start of the file and
SENTINEL_VMA_GATE, but last_addr is a signed loff_t holding a vm_end.

On sparc64, shared libraries, anonymous memory and the stack can be mapped
above 0x8000000000000000.  The rewind then does not happen and a VMA entry
is lost at a read() boundary.  Tests found missing entries in
/proc/pid/{maps,smaps,numa_maps} at many read sizes.  The proc-maps-race
selftest failed four of its six tests.  Python's sys.remote_exec()
intermittently fails when it misses the libpython data mapping in maps.

Skip the rewind only for 0 and the two sentinels instead, with an
addr_is_sentinel() helper.
