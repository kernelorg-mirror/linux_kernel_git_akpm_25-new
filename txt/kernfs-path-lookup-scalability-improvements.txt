From: Andrew Morton <akpm@linux-foundation.org>
Subject: kernfs: path lookup scalability improvements
Date: Tue, 24 Nov 2026 22:00:14 -0800

Improve kernfs scalability by keeping path lookups in RCU walk, which
takes kernfs_iattr_rwsem and the dentry reference counts out of them.
Throughput improvements of more than 40x were measured for highly
contended workloads in a 64-CPU guest.

The main work happens in kernfs_iop_permission() and
kernfs_dop_revalidate().  The latter simply stops refusing RCU walk.  In
the former the inode's mode/uid/gid are checked against the kernfs_node's
under a new per-fs seqcount.  If they match then the inode needs no
refresh and we avoid taking kernfs_iattr_rwsem.  So

        seq = raw_read_seqcount(&root->iattr_seq);
        if (seq is odd)
                slowpath;       /* a setattr is in progress */
        if (inode's mode/uid/gid != kernfs_node's mode/uid/gid)
                slowpath;
        ret = generic_permission();
        if (read_seqcount_retry(&root->iattr_seq, seq))
                slowpath;
        return ret;

where the slowpath leaves RCU walk, takes kernfs_iattr_rwsem and refreshes
the inode, as before.

The tricky part is kernfs_iop_permission()'s call of
kernfs_permission_lockless().  This lockless comparison is safe due to
three observed behaviors.  These behaviors introduce some fragility - they
must be preserved.

1: Every change to a visible node's mode or owner goes through
   __kernfs_setattr() with kernfs_iattr_rwsem held for writing, inside a
   write section of the seqcount.  The only other store to the inode's
   copies is kernfs_refresh_inode() copying from the node under the read
   lock.

   Comments were added to these sites to explain the dependency.

2: The node, its iattrs and the root are all freed through RCU.

   Comments were added to these sites to explain the dependency.

3: generic_permission() consults only the mode, uid and gid of the
   inode.  True for kernfs because it has no POSIX ACLs.

   This is an expansion of generic_permission()'s contract.  A comment
   was added to generic_permission() to explain this, with a reference
   to kernfs.

Detailed performance and correctness testing results are presented below
this patch's "---" so they can be viewed via this patch's Link:.

DETAILED DESCRIPTION AND RESULTS

Let path lookups in sysfs and cgroupfs stay in RCU walk, so that looking
up a file which is already in the dcache takes no locks and no references,
as it does on most other filesystems.  At present every lookup under /sys
leaves RCU walk at its first kernfs component.  After that it takes a
reference on each dentry and takes kernfs_iattr_rwsem for reading in each
directory, and there is only one of those for all of sysfs and one for
each cgroup hierarchy.  On a machine with many CPUs this holds all of
sysfs, and each cgroup hierarchy, to about 1.5 million lookups per second
however many CPUs are doing them.

The figures below are from KVM guests with 64 virtual CPUs in two NUMA
nodes and 16GB of memory, on a 64-core, 128-thread AMD Threadripper PRO
3995WX.  The virtual CPUs were not pinned.  The kernel was 7.4-rc3 with
the mm queue, built without lockdep, KASAN or other debug options, and
both of the kernels being compared had [2] applied.  Each figure is the
median of three or more runs of between 1 and 10 seconds.  Most were
repeated on two boots of each kernel, booted alternately.

Speedup is the change in the median rate (or, for the timed tests, in
1/time) from the kernel without this patch to the kernel with it.

access-1-cgroup-file: one process calls access(R_OK) in a loop on
/sys/fs/cgroup/t/a/b/c/d/cgroup.procs, which is already in the dcache.
1.2 million calls per second with the patch.

open-close-1-cgroup-file: as above, with open(O_RDONLY) and close().

stat-1-cgroup-file: as above, with stat().

access-8-cgroup-files: eight processes each call access() on the
cgroup.procs file of a different cgroup.  From here up the unpatched
kernel stays at about 1.5 million calls per second in total however many
processes there are.

access-64-cgroup-files: 64 processes each call access() on the
cgroup.procs file of a different cgroup.  1.39 million calls per second
in total without the patch, 67.5 million with it.

open-close-64-cgroup-files: as above, with open() and close().  1.32
million to 29.4 million.

stat-64-cgroup-files: as above, with stat().  1.37 million to 17.6
million.  stat() still takes kernfs_iattr_rwsem once, in ->getattr().

access-64-one-cgroup-file: 64 processes all call access() on the same
cgroup.procs file.  They now contend on that file's dentry.

open-close-64-one-cgroup-file: 64 processes all open and close the same
cgroup file.  Limited by the per-file mutex in kernfs_fop_open() and
kernfs_fop_release(), which this patch does not touch.

stat-64-one-cgroup-file: 64 processes all call stat() on the same cgroup
file.

access-64-sysfs-files, open-close-64-sysfs-files, stat-64-sysfs-files:
64 processes, each using /sys/devices/system/cpu/cpuN/topology/core_id
for a different N.

open-close-64-one-sysfs-file: 64 processes all open and close cpu0's
core_id.  The only test which got slower: 3% to 4% in both pairs of
boots.  It is limited by the same per-file mutex, which took 58% of the
profile without the patch and 90% with it.

access-64-enoent: 64 processes each call access() on a name which does
not exist, in a different cgroup directory.  Every call fails with
ENOENT.  This is revalidation of negative dentries in RCU walk.

access-64-tmpfs-file: 64 processes call access() on a tmpfs file of the
same depth.  The control: 13.1 million calls per second on both kernels.

access-32-during-stat: 32 processes call access() on different cgroup
files while 32 others call stat() on a different set.  The stat()
callers cost the unpatched kernel 62% of its access() rate and the
patched kernel 12%.

access-64-during-chown: access-64-cgroup-files while another process
calls chown() 1,000 times a second on a directory which the readers do
not use.  The 99th percentile of the access() latency was 710
microseconds without the patch and 1 microsecond with it.  Rates of 10,
100 and 10,000 a second, and utimensat() in place of chown(), gave the
same picture.

access-64-cgroup-files-selinux, open-close-64-cgroup-files-selinux,
stat-64-cgroup-files-selinux: the tests of those names, run from an
unconfined user with SELinux enforcing.

read-4-files-64-cgroups: 64 processes each open, read to end of file and
close cgroup.procs, cgroup.controllers, cgroup.events and cgroup.stat of
their own cgroup.  Rates are files per second.

read-4-files-one-cgroup: as above, with all 64 processes reading the
files of the same cgroup.

read-7-files-64-cgroups: 64 processes each read cgroup.events,
cgroup.procs, cgroup.stat, memory.current, memory.events,
memory.pressure and memory.stat of their own cgroup.  These are the
files which a monitor such as "below" polls.

read-7-files-one-cgroup: as above, with all 64 processes reading the
files of the same cgroup.

read-sysfs-cpu-files: 64 processes read CPU topology files under
/sys/devices/system/cpu to end of file.

read-sysfs-net-files: 64 processes read four attributes of
/sys/class/net/lo, a path which goes through a symlink.  A lookup still
leaves RCU walk at a kernfs symlink.

infiniband-1-process, infiniband-64-processes,
infiniband-200-processes: each process reads the same 4,528 files under
/sys/class/infiniband five times, through the class symlink.  The
devices are four soft-RoCE (rdma_rxe) devices on veth pairs.  With 200
processes the rate went from 723,000 to 1.44 million files per second
and system CPU time from 375 to 189 seconds.

monitor-sweep-full-path: one process reads the seven files of
read-7-files in each of 5,000 cgroups, by full path.  0.197 seconds per
sweep without the patch, 0.185 with it.

monitor-sweep-openat: as above, opening each file relative to a
directory fd for its cgroup.  0.179 seconds to 0.172.

udev-trigger-settle: time for "udevadm trigger --action=add" followed
by "udevadm settle".  0.19 seconds on both kernels.

parallel-sysfs-cat: time for "xargs -P64 -n50 cat" over 20,000 files
found under /sys.  0.12 seconds on both kernels.

systemd-cgls: time for "systemd-cgls --no-pager".  0.017 seconds on both
kernels.

cold-find-sys-devices: time for "find /sys/devices -name uevent" after
dropping the dentry and inode caches.  0.037 and 0.035 seconds, with
overlapping ranges.

One more test does not fit the table.  A single process swept 500 cgroups,
reading seven files in each, which normally takes 17 ms.  A second process
called chown() on an unrelated cgroup once a second.  A third, SCHED_IDLE
and sharing its CPU with a busy loop, called stat() on a cgroup file, so
that it was often descheduled while it held kernfs_iattr_rwsem for
reading.  The chown() then waits for that lock and everything else waits
behind the chown().  Without this patch the longest sweep in 30 seconds
took between 1.2 and 1.8 seconds.  With it the longest took 29 ms, because
the sweep's lookups no longer take the lock.  When the sweep called stat()
on each file before opening it, the patched kernel stalled as well, for up
to 556 ms, because ->getattr() still takes the lock.  This convoy was
constructed to show the effect.  It is not a reproduction of any stall
which has been reported.


kernfs is the filesystem behind sysfs and cgroupfs.  A path lookup starts
in RCU walk, which takes no locks and no references.
kernfs_dop_revalidate() and kernfs_iop_permission() both return -ECHILD
when they are called in RCU walk, so every lookup under /sys leaves RCU
walk at its first kernfs component.  After that each component costs a
dentry reference, and each directory costs a down_read() of
kernfs_iattr_rwsem and a copy of the mode and owner into the inode,
whether or not they have changed.

kernfs_dop_revalidate() already takes no locks, so let it run in RCU walk.
It has to read ->d_inode once, because in RCU walk the dentry can lose its
inode at any time.  It also reads kernfs_super_info.ns, and an RCU walk
can still be inside a superblock which is being killed, so free the
kernfs_super_info with kfree_rcu().

kernfs_iop_permission() refreshes the inode from its kernfs_node and then
calls generic_permission(), which looks only at the mode and the owner.
So compare those in the inode with those in the node.  If they are the
same there is nothing to refresh, and the check can be made without the
lock, in RCU walk and in ref walk.  If they differ, do what was done
before: return -ECHILD in RCU walk, take the lock and refresh otherwise.

The comparison on its own is not enough.  chown() changes the uid and the
gid of the node and then those of the inode.  A check which compared
before the chown() and looked at the inode half way through it would see
the new uid with the old gid, and could allow what neither owner allows.
So chmod() and chown() are now made inside a write section of a new
per-root seqcount, still under kernfs_iattr_rwsem, and the lockless check
is a read section of it.  The reader never waits for a writer: if a write
section is running, or one started during the check, it falls back to the
lock.  That is why the raw seqcount operations are used and why the write
section is allowed to sleep.

kernfs_refresh_inode() still stores the mode and owner in the inode with
kernfs_iattr_rwsem held for read and no write section.  It copies them
from the node, which cannot change while that lock is held, so during a
lockless check it can only store the values which the check has just
found there.

Every lockless check reads the seqcount, and only setattr (chmod(),
chown() and the like) writes it.  The locks in struct kernfs_root are
written all the time: ->getattr() takes kernfs_iattr_rwsem for reading on
every stat().  So the seqcount has a cacheline to itself at the end of the
struct, which grows from 232 to 320 bytes on x86_64.  There is one of
these for sysfs and one for each cgroup hierarchy.

Three things are not changed.  kernfs_iop_get_link() still returns -ECHILD
in RCU walk, so a lookup through a sysfs symlink, such as the entries of
/sys/class and of /sys/bus/*/devices, leaves RCU walk there.  ->getattr()
still takes kernfs_iattr_rwsem, so stat() takes it once per call where it
took it once per directory.  And opening a file still takes a mutex which
all the openers of that file share, which is now what limits many
processes opening the same file.

Contention here has been reported since 2021 [4], from IBM systems, from
CoreOS users, and by Brice Goglin and Fox Chen.  At Oracle, 200 processes
reading /sys/class/infiniband on a 384-CPU machine had 49% of the samples
of open() under kernfs_iop_permission(), and still had 26% there after
kernfs_iattr_rwsem was split from kernfs_rwsem to fix that [3].  The
infiniband tests above imitate that load.  Ian Kent has a report of
contention in ->d_revalidate() which he could not explain [5].  Minchan
Kim described a convoy on the rwsem when it was still global [6].

Meta's reports are of stalls, not of throughput: oomd and the "below"
monitor stuck for minutes behind a writer in kernfs_dop_revalidate() [1],
and held up for as long as 22 minutes by cgroup mkdir and rmdir waiting
for kernfs_iattr_rwsem, which every path walk takes for reading [2].  [1]
and [2] deal with those.  For a single monitor this patch is worth about
5% (the monitor-sweep tests), and it takes the monitor's lookups out of
the queue for that lock.

Correctness was tested on the same two kernels in 64-CPU guests.  A
directory of mode 0007 had its owner flipped between 1000:2000 and
2000:1000 while a process with uid 1000 and gid 1000, which must always be
refused, looked up a name in it: 35.6 million chown() calls and 125.6
million lookups in 60 seconds, and 8 million more lookups under lockdep
and KASAN, with none allowed.  3,000 rounds each of a permission-change
test and a negative-dentry test gave no wrong result.  With lockdep,
PROVE_RCU, KASAN and DEBUG_ATOMIC_SLEEP, 60 seconds of cgroup mkdir,
rmdir, chmod and chown against concurrent path walkers, 2,268 mounts and
unmounts of a private sysfs, and 2,000 renames of a veth device against
16.8 million stat() calls on its two names produced no report, and every
stat() either succeeded or failed with ENOENT.  On PREEMPT_RT with the
same debug options, the chown() test (1.2 million chown() calls and 4
million lookups, none allowed), the permission-change and negative-dentry
tests, the churn and 1,339 mounts and unmounts produced no report either.
KCSAN reported data races on both kernels.  The two which name
kernfs_iop_permission() appeared only without this patch.  Those which
appeared only with it are in the VFS's own RCU walk (lookup_fast(),
link_path_walk() and path_lookupat() against changes to dentry state),
which kernfs lookups did not reach before.  None names anything this
patch adds.  An SELinux allow or deny decision on a kernfs path was not
tested: the SELinux runs exercised only the mode bits.

Earlier work on this:

2021  Ian Kent turned the global kernfs_mutex into an rwsem and cached
      negative dentries [4].  Early versions of that series had a patch
      to stay in RCU walk.  It was dropped in v3 because "it doesn't
      actually give very much improvement" and "if there's a place where
      mistakes could go unnoticed it would be in that path".
2021  Minchan Kim made the rwsem per-filesystem [6].
2022  Imran Khan replaced the global open-file mutex with hashed ones
      [7].  Ian Kent took i_lock out of the inode refresh [8].
2023  Imran Khan split kernfs_iattr_rwsem from kernfs_rwsem [3].
2024  Tejun Heo made kernfs_nodes RCU-freed [9].
2025  Sebastian Andrzej Siewior made a node's name and parent readable
      under RCU [10].
2026  Shakeel Butt made kernfs_dop_revalidate() lockless and left
      lifting its LOOKUP_RCU bail "to a separate series" [1], took work
      out from under the kernfs_rwsem write lock [11], and stopped mkdir
      and rmdir taking kernfs_iattr_rwsem for writing [2].  The last of
      those is not yet upstream, and this patch goes on top of it.
